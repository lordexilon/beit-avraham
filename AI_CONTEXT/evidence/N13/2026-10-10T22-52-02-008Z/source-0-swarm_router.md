# 🐝 Swarm Router Protocol (SCA v3.0 - CQRS)

This workflow is triggered **WHENEVER** the user requests development, modification or refactoring. It replaces the old linear flow.

> [!WARNING]
> **FORBIDDEN:** Under no circumstances manually edit `AI_CONTEXT/swarm_ledger.md` or `AI_CONTEXT/metricas_sca.md`. These files are read-only mirrors generated by the SCA Matrix.

## Phase 1: Analysis and Graph (DAG) Design

1. **Read the Environment and Analyze the Structure:**
   - Review `AI_CONTEXT/active_context.md` and `AI_CONTEXT/memory_schema.md`.
   - Use **Codebase Memory MCP** to query the local dependency graph (tree-sitter).
   - **CRITICAL:** Check `AI_CONTEXT/swarm_ledger.md` to identify the last Node number used. Continue the numeric sequence (e.g. if the last one is N13, your first node must be N14).
2. **Break Down the Task and Diagram the Architecture:**
   - Split the request into logical "Nodes", identifying parallelism and dependencies.
3. **Early Persistence (SCA Studio Monitor):**
   - **BEFORE** waiting for approval, IMMEDIATELY inject your new proposed DAG using the CLI. For each node run:
     ```bash
     node scripts/log_sca.js --type ledger --project_name "[YourProject]" --sprint_name "[SprintName]" --node_id "[N_X]" --task_desc "[Desc]" --status "⏳ Pendiente"
     ```
4. **Emit the Context Bridge (Swarm Edition):**
   Present the plan to the user for approval.

## Phase 2: Swarm Execution (With Real-Time Monitoring)

Once the user approves the Context Bridge:

### If Mode is STRICT (Human-in-the-Loop):
1. **Execute the Current Node:** Process ONLY the corresponding node.
2. **Real-Time Update (MANDATORY):** Open the approved node with `task_workflow.cjs start` before work. After verification, close with `task_workflow.cjs finish`. Do not mark completed merely because code was generated. The ledger command below is for reconciliation only after capture, time and evaluation have been persisted:
   ```bash
   node scripts/log_sca.js --type ledger --project_name "[YourProject]" --sprint_name "[SprintName]" --node_id "[N_X]" --task_desc "[Desc]" --status "✅ Hecho"
   ```
3. **Pause and Return Control:** Show the generated diffs to the user and wait for approval for the next node.

### If Mode is AUTONOMOUS (Autopilot):
1. Fire the nodes. As EACH node finishes, update it to `✅ Hecho` via CLI immediately, without waiting for the others.

## Phase 3: Final Closing

1. **Node Reconciliation (Sweep):** Review `AI_CONTEXT/swarm_ledger.md`. If you identify pending nodes whose work was already completed, force their update to `✅ Hecho` via CLI.
2. **Update Active Context:** Modify `AI_CONTEXT/active_context.md` (this one IS editable) to reflect the new global state of the architecture.
3. **Evidence-based measurements:** Prepare a JSON with project_name, sprint_name, node_id, unique task_key and task_desc. Use:
   ```bash
   node scripts/task_workflow.cjs start AI_CONTEXT/task.json
   node scripts/task_workflow.cjs finish AI_CONTEXT/task.json
   ```
   Record a sourced comparable reference before execution with task_evaluation.cjs when available. Closing persists capture, time, evaluation and Done in that order. Retry failed closing steps rather than bypassing them. Missing reference or acceptance remains pending.

4. **Measurement limits:** Repository token count is not a baseline. Cached input is not SCA savings. Conversation windows do not prove exclusive task usage. Agent time does not substitute human active time. Keep confirmed charges, subscription allocation, API equivalents and local operating costs separate. Do not start a permanent watcher without authorization or double-count overlapping timing windows.

5. **Comparative evidence:** Follow AI_CONTEXT/comparative_pilot.md. Register every proposed node Pending before execution. In progress means execution started. STRICT retains approval between nodes. Preserve negative outcomes and report scope and sample size.
